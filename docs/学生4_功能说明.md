# 学生 4 功能说明：移库出库管理

## 1. 模块边界

学生 4 负责“移库出库管理”功能包，位于 Django 应用 `warehouse`。上游基础数据（药材、库位、库存批次、用户）在本项目中一并提供，保证学生 4 的模块可以独立运行和验收；下游的库存查询、统计报表与导出由学生 5 负责，可通过 `StockMovement`、`OrderStatusLog` 直接扩展，不需要改动本模块的业务表。

本模块解决的核心问题：

1. 移库/出库任务从创建到执行缺少统一记录；
2. 库存变动与业务单据难以对应；
3. 审核、执行、异常处理缺少岗位分离与可追溯留痕；
4. 并发或重复确认可能造成重复扣减/超卖。

## 2. 需求对应关系

| 任务书子功能 | 实现位置 | 验收观察点 |
| --- | --- | --- |
| ① 移库出库管理任务/记录处理 | `views.transfer_create/edit/delete`、`views.outbound_create/edit/delete`、`services.submit_order` | 新建、编辑、删除草稿；保存并提交；服务端库存预检；移库/出库字段完整 |
| ② 移库出库管理审核、确认或状态流转 | `services.approve_order/reject_order/complete_*/cancel_order`、`order_detail.html` | 主管通过/驳回；仓管确认执行；状态轨迹；禁止自审；重复执行保护 |
| ③ 异常备注、附件上传或历史记录追踪 | `services.record_exception`、`OrderAttachment`、`OrderStatusLog`、`StockMovement` | 追加式异常备注；附件类型/大小限制；完整操作时间线；库存前后值可追溯 |

## 3. 角色与权限

| 角色 | 实现 | 权限 |
| --- | --- | --- |
| 仓管员 `keeper` | `UserProfile.Role.KEEPER` | 建单、编辑本人草稿/驳回单、提交、执行已审核单、异常备注、附件 |
| 仓库主管 `manager` | `UserProfile.Role.MANAGER` | 审核通过、驳回、取消未完成单、异常备注、附件 |
| 管理员 `admin` | `UserProfile.Role.ADMIN` / superuser | 全部权限；可进入 Django Admin |
| 只读访客 `viewer` | `UserProfile.Role.VIEWER` | 仅查看列表、详情、审批意见、附件、轨迹 |

权限判定分三层：

1. 模板：隐藏无权按钮（`can_review`、`can_complete`、`can_edit` 等）；
2. 视图：`login_required` + 角色判断，越权返回 403；
3. 服务层：审核人不能是申请人，取消/状态流转再次校验，防止绕过前端。

## 4. 数据模型

```text
Warehouse 1 ─── n StorageLocation 1 ─── n StockBatch n ─── 1 Herb
                                          │
                                          └── n StockMovement

User 1 ─── 1 UserProfile

TransferOrder ─┬── n OrderAttachment
               └── n OrderStatusLog（按 order_type + order_id 关联）
OutboundOrder ─┘

TransferOrder: 药材 + 批次 + 移出库位 + 移入库位 + 数量 + 原因
OutboundOrder: 出库类型 + 药材 + 批次 + 库位 + 数量 + 领用人 + 用途
```

关键字段：

- `StockBatch.quantity`：库存唯一事实来源，按“药材 + 库位 + 批次”唯一；
- `OrderBase.status`：六态状态机；
- `review_comment`：审核意见；
- `exception_note`：追加式异常备注；
- `submitted_at / audited_at / completed_at`：关键节点时间；
- `OrderStatusLog`：操作类型、原状态、新状态、操作人、说明、时间；
- `StockMovement`：变动类型、数量、变动前/后、关联单号、操作人。

## 5. 状态机与业务规则

### 5.1 状态定义

| 状态 | 中文 | 含义 |
| --- | --- | --- |
| `draft` | 草稿 | 可编辑，不占用库存 |
| `pending` | 待审核 | 已提交，等待主管处理 |
| `approved` | 已审核 | 审核通过，等待仓管执行 |
| `completed` | 已完成 | 库存已联动，不可重复执行 |
| `rejected` | 已驳回 | 可编辑后重新提交 |
| `cancelled` | 已取消 | 终态，不再影响库存 |

### 5.2 动作矩阵

| 动作 | 前置状态 | 允许角色 | 效果 |
| --- | --- | --- | --- |
| 创建 | — | 仓管/管理员 | 生成 `YK...` / `CK...` 单号，状态 draft |
| 编辑 | draft / rejected | 申请人/管理员 | 更新字段；驳回单编辑后回到 draft |
| 删除 | draft | 申请人/管理员 | 删除草稿、附件文件与草稿轨迹 |
| 提交审核 | draft / rejected | 申请人/管理员 | 校验同仓、库位不同、批次存在、库存足够；→ pending |
| 审核通过 | pending | 主管/管理员 | 记录审核人、时间、意见；→ approved |
| 驳回 | pending | 主管/管理员 | 驳回原因至少 2 字；→ rejected |
| 确认移库 | approved | 仓管/管理员 | 锁源库存；源减、目标增；写 2 条流水；→ completed |
| 确认出库 | approved | 仓管/管理员 | 锁库存；扣减；写 1 条流水；→ completed |
| 取消 | draft/pending/approved | 申请人对本人 draft/pending；主管/管理员对未完成单 | → cancelled，保留轨迹 |
| 追加异常 | 非 cancelled | 仓管/主管/管理员 | 追加带时间/操作人的备注，不改变状态 |
| 上传附件 | 任意 | 仓管/主管/管理员 | 校验扩展名与 5 MB 上限，写入附件档案与轨迹 |

### 5.3 库存一致性

- 提交时预检可防止明显超量进入审核队列；
- 执行时在 `transaction.atomic()` 中通过 `select_for_update()` 锁定源库存行，再复核数量；
- 移库目标批次不存在时自动创建，并继承源批次的生产日期/有效期；
- 任何一步失败（库存不足、状态变化、数据库异常）整笔回滚，不会出现“单据完成但库存没动”；
- 只有 approved 状态可执行，配合行锁避免重复点击/并发确认造成重复扣减；
- 审核通过不扣库存，真正扣减发生在“确认执行”，符合“审核授权 / 仓管执行”的职责分离。

### 5.4 异常备注

- 不覆盖历史，追加格式：`[2026-10-30 15:40 陈远志] 备注内容`；
- 执行失败时，若单据仍为 approved，系统自动把失败原因追加为异常备注，便于复盘；
- 已取消单据禁止追加；已完成单据允许补充事后异常说明；
- 每次追加都会写入 `OrderStatusLog`，轨迹中显示操作人、时间和备注摘要。

### 5.5 附件

- 支持：`pdf / png / jpg / jpeg / webp / doc / docx / xls / xlsx`；
- 单文件 ≤ 5 MB；
- 一条附件只能关联一张移库单或一张出库单，由模型 `clean()` 与表单共同保证；
- 上传后写操作轨迹；已完成单据的附件仅主管/管理员可删除；
- 附件存放在 `media/order_attachments/YYYY/MM/`，文件名随机化，保留原始文件名用于展示。

## 6. 事务与并发

`services.py` 中所有库存动作均为独立事务：

```python
with transaction.atomic():
    order = TransferOrder.objects.select_for_update().get(pk=order.pk)
    source = StockBatch.objects.select_for_update().filter(...).first()
    ...
```

- 先锁单据，避免同一单据被并发重复确认；
- 再锁库存行，避免两张单同时消耗同一批次；
- SQLite 下行锁是弱化的，但生产 MySQL/PostgreSQL 会真正阻塞并发写；
- 测试覆盖“库存被其他操作改小后确认失败并回滚”的场景。

## 7. 与小组项目的合并方式

1. 复制 `warehouse/` 到小组项目，加入 `INSTALLED_APPS`；
2. 将 `warehouse/urls.py` 挂到根路由；
3. 保留或映射 `UserProfile` 的角色字段；如小组已有角色体系，只需替换 `permissions.py` 的角色判断；
4. 保留 `Herb / StorageLocation / StockBatch` 作为共享基础数据；如学生 2 已有同名模型，可通过外键或数据迁移合并；
5. 学生 5 的查询/统计/导出可直接读取 `StockMovement` 与 `OrderStatusLog`，无需修改本模块接口。

## 8. 已知边界与扩展建议

- 当前审核为单级审核；多级会签可增加 `approval_step` 表；
- 审核通过未做库存预留，极端情况下可在执行前被其他单占用，系统会在执行时拦截并记录异常；如需强预留，可增加 `reserved_quantity`；
- 附件未做病毒扫描，生产环境可接入对象存储与安全扫描；
- 未实现批量导入/导出，学生 5 可在现有流水表上扩展；
- 演示数据中的密码为弱口令，仅用于课程验收。
